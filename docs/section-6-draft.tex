\section{Comparative evaluation}
\label{sec:evaluation}

Table~\ref{tbl:comparison} compares frameworks by what they can express. An
engineer deciding whether to adopt RDF-Connect also needs to know what that
expressiveness costs, and this section measures it. We report three results.

First, the overhead of the framework is small and predictable: a fixed start-up
cost per pipeline and a constant cost per message per hop, which an engineer can
estimate before building a pipeline (Section~\ref{sec:eval-micro}).

Second, RDF-Connect and batch workflow systems cannot be compared on runtime
alone, because they were built for different requirements. A workflow system
executes a finite job over complete input files; RDF-Connect was designed for
sources that never finish. We therefore take a pipeline that is deployed and in
use, and compare RDF-Connect with the way a workflow system would realistically
keep its output current, by re-running a batch job on a schedule
(Section~\ref{sec:eval-pipeline}). This exposes a trade-off between freshness
and compute that streaming does not have.

Third, a pipeline has to be written and maintained. We measure that cost as the
lines of configuration needed to describe the pipeline and to change it
(Section~\ref{sec:eval-config}).

In every experiment, all systems run the same processor implementations, and
every run is checked against output derived from the input, so that a system
cannot appear fast by doing less work. The benchmark, the recorded input, the
pipeline definitions and all raw measurements are published, so that the
experiments can be rerun or extended with other systems.

\subsection{What the framework costs}
\label{sec:eval-micro}

To isolate the framework, the first experiment keeps the processors fixed and
removes everything else. Two configurations run the same processor classes over
the same workload. The first is an ordinary RDF-Connect deployment. The second
is a driver that constructs the processors in one process and connects them with
in-memory channels. These channels reproduce the acknowledgement semantics of
the runner: a write resolves only once the reader has consumed the message. The
difference between the two configurations is therefore the orchestrator, the
runners and the gRPC transport. The workload is synthetic: a generator, a chain
of pass-through processors and a sink, parameterised by message count, message
size, chain depth, and the CPU time each processor spends per message.

\paragraph{Fixed cost.} Starting a pipeline with one runner takes 1.7\,s, against
0.13\,s for the in-process driver. A second runner in another language, as in
any pipeline that combines JVM and Node.js processors, raises this to 2.1\,s.
The cost is paid once per pipeline, not per message.

\paragraph{Cost per message.} With processors that do no work, a message
crosses the framework in 0.18\,ms (median), against 0.002\,ms in process, and
the framework sustains about 5\,600 messages per second. Figure~\ref{fig:eval-overhead}
shows what happens as processors do real work. The time the framework adds per
message grows only slowly, from 0.18\,ms with no work to 1.5\,ms with
100\,ms of work, so its share of the total falls: 70\,\% at 0.1\,ms of work,
33\,\% at 1\,ms, 7\,\% at 10\,ms and 1.5\,\% at 100\,ms.
Following Task Bench~\citep{slaughter2020}, we summarise this as the minimum
effective task granularity, the work per message at which half of the time is
spent in the framework. For RDF-Connect it is about 0.35\,ms.

\paragraph{Cost per hop.} Each processor added to a chain adds 0.14\,ms to a
message's latency, against less than 0.001\,ms in process: a message crosses a
chain of eight pass-through processors in 1.3\,ms. The overhead of a pipeline is
thus the per-hop cost times its depth, plus the fixed start-up cost.

\paragraph{Message size.} Messages up to 64\,KiB cost under 0.5\,ms. A 1\,MiB
message costs 6.1\,ms, and messages of 10\,MiB fail, because they exceed the
maximum message size of the gRPC transport. \res{Confirm cause; point to the
streaming channel mode for large payloads.}

  (a)~Median latency per message through RDF-Connect and through the in-process

  (b)~The share of the latency spent in the framework. The dashed line marks

\paragraph{Where real processors sit.} Measured in isolation, the two heaviest
stages of the pipeline in Section~\ref{sec:eval-pipeline} cost 0.60\,ms
(mapping) and 0.39\,ms (validation) per record once warm. These are just above
the threshold, so for record-at-a-time processing of this kind the framework is
noticeable but not dominant. Two consequences follow for pipeline authors.
Batching records into larger messages amortises the per-hop cost. Starting a
process is far more expensive than passing a message: one extra start of the
mapper costs as much as 1\,700 warm records, and one extra start of the
validator 700. This matters in Section~\ref{sec:eval-pipeline}, where the batch
systems start their processes once per invocation.

\subsection{Keeping a stream current}
\label{sec:eval-pipeline}

The second experiment uses a real pipeline, published by a third party and not
written for this paper. We first describe the pipeline and the systems, then
measure a single run over a fixed input, which checks the framework overhead of
Section~\ref{sec:eval-micro} under a real workload. We then measure the setting
the pipeline was built for, where input keeps arriving and the output has to be
kept current.

\subsubsection{The pipeline and the data}

\texttt{CA-Blue-Bike-LDES} (Section~5) publishes the availability of a Belgian
bike-sharing service as a Linked Data Event Stream. It polls an HTTP API for the
state of every station, maps each response to RDF, validates it, detects which
stations changed, annotates the changes as stream members, fragments them by
time and writes the fragments as a static LDES.
Table~\ref{tab:eval-stages} lists the stages. Three of the six are stateful:
change detection remembers the last version of every member, the fragmenter
remembers its buckets, and the writer appends to the tree it has already
published.

The RML mapping and the SHACL shapes are those of the deployment. The mapping
was changed in one line, so that it reads from a channel instead of the live
API. The input was recorded from the API that the deployment consumes, so every
run replays the same data. One \emph{snapshot} is one response of the API: the
state of all 327 stations at one moment. Of these stations, 70 carry the
timestamp that the mapping uses to identify observations. All 70 stream members
are created within the first five snapshots; after that, the stream grows by
about 2.4 updates per snapshot.

\subsubsection{The systems}

Workflow systems are the closest alternative to RDF-Connect for this kind of
pipeline, and the Common Workflow Language (CWL)~\citep{crusoe2022cwl} is the most
widely adopted standard among them. A CWL workflow is not bound to one
implementation, so we run the same workflow documents on three engines:
cwltool, the reference implementation; Toil~\citep{vivian2017toil}, designed for large
clusters; and StreamFlow~\citep{colonnelli2021streamflow}, designed for hybrid cloud and HPC
deployments.\footnote{cwltool 3.2.20260720092025, Toil 9.5.0 and StreamFlow
0.2.0rc3, without containers.} The systems compared are the following.

\begin{description}
\item[RDF-Connect.] One pipeline description; the mapper runs on the JVM runner
  and the other five processors on the Node.js runner.
\item[Shell pipeline.] The six stages as command-line programs connected by
  Unix pipes, with named pipes for the side channels. It runs the same
  processes as RDF-Connect with the operating system in place of the
  orchestrator. It has no declarative description and no validation, and serves
  as a lower bound on what connecting the stages can cost.
\item[CWL.] One \texttt{CommandLineTool} per stage and a workflow that runs each
  stage once over its complete input, passing files between stages.
\end{description}

The command-line programs are not reimplementations. A small adapter
instantiates a published processor from an RDF description of the step, reads
its arguments through the processor's own SHACL shapes as the runner does, and
connects its channels to standard input and output. All systems therefore run
the same processor code with the same configuration.

A workflow system can also split the input and run a task per snapshot, using
CWL's \texttt{scatter} or Nextflow's~\citep{ditommaso2017nextflow} channels. We measured both
and do not treat them as separate arms. A scattered workflow still starts only
once its input is complete, so it does not help keep the output current, and
only the two stateless stages at the front of the pipeline can be scattered at
all. Every task also starts its own JVM or Node.js process, which is what the
stage costs above predict to be expensive: over 60 snapshots, one task per
snapshot costs 11$\times$ the CPU time of the single batch run under CWL
(835\,s against 76\,s) and 12$\times$ under Nextflow. Scattering into two tasks
of 30 snapshots still costs 1.35$\times$.

\subsubsection{Setup and correctness}

All experiments run on one machine: \res{a four-vCPU KVM virtual machine,
15\,GiB of RAM, Ubuntu 24.04.4 on Linux 6.8.0}, with Node.js 24.21.0, OpenJDK
21.0.12.1 and Nextflow 26.04.6. Working directories are on tmpfs, so the
systems that pass files are not measured against the disk. Each run executes in
its own cgroup, from which CPU time and peak memory are read; this includes
short-lived processes that sampling would miss. Each configuration runs five
times, and we report medians.

Each run is checked against output derived from the recorded input rather than
from another system. A member is created the first time a station is observed
with a given timestamp, and updated when data reachable through the member
shape changes. Timestamps that the pipeline generates itself are excluded,
since they differ between runs by design. All \res{320} runs reported in this
section published exactly the members and updates implied by their input.

RDF-Connect, the shell pipeline and the CWL workflow on cwltool and StreamFlow
all spend 0.76--0.78\,s of CPU time per additional snapshot. The difference
between them lies entirely in the fixed cost: RDF-Connect spends 45\,s where the
shell pipeline and CWL spend 29--31\,s. This agrees with
Section~\ref{sec:eval-micro}. A snapshot crosses six hops, which the
microbenchmark prices at about 1\,ms in total, less than 0.2\,\% of the
0.76\,s the processors spend on it, and too little to show up in the fit.
\res{The extra fixed cost is larger than the 1.7--2.1\,s start-up measured in
Section~\ref{sec:eval-micro}; decompose it (runner start-up, processor
loading, JIT warm-up) before attributing it.} As a result, RDF-Connect's
relative overhead shrinks as the input grows: it spends 36\,\% more CPU than
CWL over 5 snapshots and 17\,\% more over 60.

Elapsed time tells a different story. The shell pipeline finishes in less than
half the time of RDF-Connect, because it keeps 2.9 cores busy against 1.6.
The transport is not the cause, since 60 snapshots at 1\,ms each account for
well under a second. The cause is concurrency: an RDF-Connect channel admits
one message at a time, so consecutive stages advance in lock-step, whereas a
Unix pipe lets a producer run ahead of its consumer into a kernel buffer. The
CWL workflow runs one stage at a time and uses a similar 1.5 cores. RDF-Connect
therefore matches the batch workflow in elapsed time as well as in cost per
snapshot, and the shell pipeline shows how much concurrency both leave unused on
this machine.

Memory and storage go in opposite directions. The streaming systems keep all six
stages resident at once and peak at 1.9--2.1\,GB; CWL holds one stage at a time
and peaks at 1.1--1.2\,GB. In exchange, CWL writes the output and the state of
every stage to disk, 42\,MB over 60 snapshots, where the streaming systems keep
both in memory.

The three CWL engines differ as implementations, not as models. cwltool and
StreamFlow are within 3\,\% of each other in CPU time; Toil follows the same
line at a higher fixed cost, with a fixed elapsed time of 43\,s against 17\,s. Running one valid
workflow on three engines was nonetheless not effortless. StreamFlow wrote a
tool's standard error into the file capturing its standard output, and staged
an array of files with identical names into one directory, where they
overwrote each other. Both silently produced wrong output until worked around.
Toil retries a failed job with more memory by default, which hides failures in
the timings.

\subsubsection{Keeping the output current}
\label{sec:eval-fresh}

A single run over a fixed input is how a batch system is normally evaluated,
but it is not how this pipeline is used. The deployment runs continuously and
publishes each change shortly after the API reports it. A batch step starts
only when its input files are complete, and a source that never ends never
produces a complete file. A workflow system can still approximate the
deployment by running the workflow repeatedly on a schedule, as a cron job or a
scheduled CI workflow would. There are two ways to do this.

\begin{description}
\item[Rebuild.] Every run processes the entire history received so far, from
  scratch. No state is kept between runs, so each run is self-contained.
\item[Incremental.] Every run processes only the snapshots that arrived since
  the previous run. The state of the three stateful stages must then be carried
  from one run to the next: the change detector's memory of every member, the
  fragmenter's buckets, and the published tree that the writer appends to. In
  CWL this state travels as files and directories, which the workflow has to
  accept as inputs and return as outputs.
\end{description}

We replay 60 snapshots, arriving every 10\,s, over ten minutes.
\res{Relate 10\,s to the deployment's polling interval.} RDF-Connect and the
shell pipeline consume each snapshot as it arrives. The CWL workflow runs every
$k$ arrivals, for $k \in \{2, 6, 12, 30\}$, in both modes. \emph{Freshness} is
the time from a snapshot's arrival to the publication of the changes it causes;
snapshots that cause no change are excluded. \emph{Cost} is the CPU time spent
over the whole window, including idle time for the streaming systems.

Figure~\ref{fig:eval-freshness} and Table~\ref{tab:eval-fresh} show the result.
The streaming systems publish a change a median of 0.6\,s (RDF-Connect) and
1.0\,s (shell) after it arrives, at a cost of 107 and 82\,s of CPU over the ten
minutes. Every scheduled arm is at least an order of magnitude less fresh, and
the arms that come closest cost several times more CPU.

Scheduled execution has a freshness floor. Every run pays the fixed cost of
starting the workflow and its processes, which Table~\ref{tab:eval-systems} puts
at about 30\,s of CPU and 17\,s of elapsed time. No schedule can publish faster
than one run takes, and the freshest scheduled arm, incremental with $k=2$,
publishes 26\,s after arrival while spending 7$\times$ the CPU of RDF-Connect.
Running less often lowers the cost but adds waiting time: a snapshot waits on
average half an interval before the next run begins. At the far end of this
range, a schedule hardly differs from a single batch job. With 60 snapshots,
incremental runs every 30 arrivals are just two runs, each over one half of the
input: the dataset is processed exactly once, split in two. This is the only
schedule at which the batch workflow matches the CPU cost of RDF-Connect (108
against 107\,s), and it publishes a change a median of 173\,s after it arrives,
about 300 times later.

Processing all 60 snapshots in one run at the end of the window would be
cheaper still. Table~\ref{tab:eval-systems} puts such a run at 76\,s of CPU,
against 89\,s for RDF-Connect over the same input and 107\,s for keeping
RDF-Connect running for the ten minutes. On compute alone the batch workflow
therefore wins, and what it gives up is freshness: its output is up to ten
minutes old when it appears. Streaming keeps the output current for 31\,s of
CPU more than that single run. A schedule pays for every step towards freshness
with further invocations, each carrying the fixed cost of a run: incremental
runs every two arrivals spend 700\,s more to publish a change after 26\,s.

Rebuilding costs more because every run reprocesses the whole history, and the
work grows with it. With $n$ snapshots and a run every $k$ arrivals, a rebuild
processes about $n^2/2k$ snapshots in total where streaming processes $n$. At
$k=2$ this has a visible consequence: runs soon take longer than the 20\,s
between them, so they fall further behind with every run. Freshness grows
without bound, to 450\,s for the last snapshot, and the last run finishes seven
minutes after the final snapshot arrived. Extrapolated to a day of this feed at
one snapshot per minute and hourly rebuilds, the rebuild idiom processes about
18\,000 snapshots where streaming processes 1\,440. Resetting the history
periodically bounds this growth, at the price of losing continuity in the
published stream. A rebuild also generates fresh publication timestamps for
members that were already published, so consumers of the stream see every
member change on every run.

The incremental mode avoids the growing history but pays for it in the workflow
itself. The state of three stages must be written out, returned as workflow
outputs and supplied as inputs to the next run, and the CWL workflow needed an
additional optional input to receive the previously published tree before
scheduled runs published correct output. In RDF-Connect the same state simply
remains in the memory of the running processors.

\subsection{What a description costs}
\label{sec:eval-config}

The last cost is paid by the person who writes and maintains a pipeline. We
measure it in lines of configuration, counting lines that are neither blank nor
comments. Both systems split this configuration into two layers
(Figure~\ref{fig:eval-config}). The first describes a processor: in RDF-Connect
its SHACL contract (Section~\ref{sec:shacl}), in CWL a \texttt{CommandLineTool}.
It is written once, by whoever packages the processor, and can be published and
reused by every pipeline that needs the processor, through the RDF-Connect
registry (Section~\ref{sec:ecosystem}) or through a registry of CWL tools such
as Dockstore or WorkflowHub. The second layer is written for one pipeline: which
processors it uses, how each is configured, and how they are connected. The CWL
tool descriptions for this benchmark did not exist, because the processors had
never been packaged as command-line tools, so we wrote them; the comparison
below treats them as if they had been published, as the RDF-Connect contracts
were.

\begin{figure}[pos=htbp]
  \centering
  \includegraphics[width=\columnwidth]{figures/eval-config.pdf}
  \caption{Lines of configuration, counting lines that are neither blank nor
  comments. Top: the descriptions written once per processor, which can be
  published and reused (the SHACL contracts of five of the six stages, and the
  six CWL tool descriptions). Middle: the configuration written for this
  pipeline. Bottom: the change to that configuration when one processor is
  added.}
  \label{fig:eval-config}
\end{figure}

\paragraph{Per pipeline.} Describing the Blue Bike pipeline takes 105 lines for
RDF-Connect, in one document that holds the processors, their configuration and
the channels between them. The CWL encoding takes 157 lines across seven files:
a workflow of 62 lines, a job file of 10 lines, and 85 lines that configure the
five Node.js stages. Adding a processor, skolemisation, changes 10 lines of the
RDF-Connect document. In CWL it changes 17 lines across three files: seven in
the workflow, one in the job file and a new configuration file of nine lines.
The modified RDF-Connect pipeline was run and published the expected output;
the modified CWL workflow was validated.

These counts favour RDF-Connect somewhat. The step configuration of the CWL
encoding is written in the RDF format that our command-line adapter reads, with
its own prefixes and declarations, whereas a tool designed for the command line
would take most of these settings as arguments. The difference in line count
would then shrink. What remains is a difference in structure: an RDF-Connect
pipeline is a single document, while a CWL pipeline spreads its configuration
and its wiring over a workflow, a job file and one file per configured step.

\paragraph{Per processor.} The processor descriptions show the opposite. The
SHACL contracts of five of the six stages take 366 lines, about 73 per
processor; the mapper's contract ships inside its jar and is not counted. The
six CWL tool descriptions take 144 lines, about 24 per tool. Our tool
descriptions are short partly because they say little about the processor: each
passes the processor's configuration as a single file, so a CWL engine can check
that the right files reach the right steps, but not that the configuration
inside them is valid. A SHACL contract declares every parameter of the
processor, with its datatype, its cardinality, a label and a description. A CWL
tool with a typed input for every parameter would provide part of this, and
would grow towards the size of the contract.

\paragraph{What the contracts buy.} The additional lines in the contracts are
what make the pipeline layer easier to write. Because every parameter is
declared, a pipeline can be validated against the contracts of its processors
before it starts: a missing argument, a value of the wrong datatype or a
channel without a reader is reported before any data flows, instead of
surfacing as a failure partway through a run. The same declarations support the
author while writing: the pipeline generator of Section~\ref{sec:ecosystem}
renders each contract as a form, and the MCP server gives coding agents the
contracts, so that the configuration they propose can be checked against the
interface the orchestrator will enforce. The contracts also document the
processor, since the label and description of every parameter are part of them.

For a pipeline assembled from processors that have already been described,
writing the pipeline therefore takes a comparable amount of configuration in
both systems, somewhat less in RDF-Connect, and in one document instead of
seven. Describing a processor takes more in RDF-Connect. That cost is paid once
by the processor's author, and every pipeline that uses the processor inherits
the validation, the authoring support and the documentation it provides.

\section{Comparative evaluation}
\label{sec:eval}

Feature matrices such as Table~1 say what a framework can express, not what
that expressiveness costs. This section measures the cost. The difficulty is
that RDF-Connect and the systems it is naturally compared with are optimised
for different points in the workload space: a batch system over files pays per
process and per file, a streaming system pays per message. A single pipeline
run at a single size would therefore pick the winner before any code runs. We
address this with three commitments, and report the results as a function of
the workload rather than as a single number.

\paragraph{The same executables in every system.} Every system runs the
identical RML mapper and SHACL validator. In RDF-Connect they are the
published processors (\texttt{rml-processor-jvm}, \texttt{shacl-processor-ts});
everywhere else they are thin command-line wrappers around the same library
calls, built from the same source (\texttt{rml-map}, \texttt{shacl-validate}).
Warm-up state is not shared across invocations, because it is exactly what
distinguishes the systems. Whatever differs between systems is therefore the
composition, not the computation.

\paragraph{The same semantics in every system.} The SHACL stage has two
outputs in every system, as the processor has: the data of every unit that
conforms in full, and a validation report for every unit that does not. SHACL
defines a verdict but not what to discard; any rule finer than the processor's
own would be an invention of the benchmark, so none is used.

\paragraph{Correctness is checked, not assumed.} The generator records which
records it broke. From that alone, without running any system, the expected
output of every run is derived: the mapped quads of every unit without a
broken record, and one report per unit with one. Every run is compared against
it exactly, and a run that does not match is reported as failed rather than
timed.

\subsection{Systems under comparison}
\label{sec:eval-systems}

\begin{description}
\item[RDF-Connect.] The orchestrator with the JVM runner hosting the RML
  mapper and the Node.js runner hosting the SHACL validator, a source, and two
  sinks. Every message crosses the orchestrator (Section~3.4).
\item[Shell pipe.] \texttt{rml-map | shacl-validate}, both streaming,
  stdin to stdout. It is RDF-Connect without the orchestrator: the same two
  warm processes, connected by the operating system instead. It answers the
  question a sceptical reader asks first: what does the declarative, validated
  description cost over piping the programs together?
\item[CWL.] One \texttt{CommandLineTool} per stage, composed into a workflow,
  in two encodings. \emph{Batch} runs one task per stage over the whole input,
  as a CWL user would write it. \emph{Scatter} splits the input into chunks and
  runs the stateless stages once per chunk, then gathers; CWL never splits files
  itself, so the split and the gather are steps of the measured workflow. Only
  the stateless prefix can be scattered (\S\ref{sec:eval-capability}), and the
  stateful stages carry their state between tasks as staged inputs and
  outputs. To separate the language from one implementation of it, the
  identical workflow runs on three runners: \texttt{cwltool}
  \res{3.2.20260720092025}, the reference implementation; Toil \res{9.5.0}, a
  production runner; and StreamFlow \res{0.2.0rc3}. All run without
  containers.
\item[In-process driver.] The processors of the synthetic pipeline wired
  directly with in-memory channels, used in \S\ref{sec:eval-overhead} as the
  zero-overhead reference against which the orchestrator's own cost is
  measured.
\end{description}

\subsection{Workloads}
\label{sec:eval-workloads}

\paragraph{Knowledge graph construction and publication (B1).} The workload is
the pipeline behind one of the deployments of Section~5, \texttt{Blue-bike}:
snapshots of a bike-sharing availability API are lifted to RDF, checked, turned
into a feed of changes, annotated as a stream, fragmented and published as a
Linked Data Event Stream.

\begin{center}
\begin{tabular}{llll}
\toprule
\# & Stage & Component & KE task (\S5.5) \\
\midrule
1 & semantic lifting & \texttt{RmlMapper} (JVM) & lifting \\
2 & quality gate & \texttt{Validate} (TS) & validation \\
3 & change detection & \texttt{DumpsToFeed} (TS) & change management \\
4 & stream annotation & \texttt{Sdsify} (TS) & --- \\
5 & fragmentation & \texttt{Bucketize} (TS) & fragmentation \\
6 & publication & \texttt{LdesDiskWriter} (TS) & publication \\
\bottomrule
\end{tabular}
\end{center}

Nothing here was written for the benchmark. The components are the published
processors, and the mapping is the deployed pipeline's own RML document (nine
triples maps over the mobility vocabularies, with FnO functions), changed in
one line so that its source is the pipeline's channel rather than the live API.
The stages span two language runtimes, so B1 is also the cross-environment case
of the outline's B3.

The data is the API the deployment consumes, recorded once into an archive so
that runs replay identical input: \res{330} stations per snapshot, of which
\res{70} carry the timestamp the mapping keys reports on, and \res{3.6}
stations change per minute.

\paragraph{Correctness.} A member's IRI carries the station and the timestamp
it was last seen, so the members a correct run publishes are exactly the
distinct pairs in the input. Every run is checked against that, computed from
the input rather than from any system's output; the timestamps the pipeline
itself invents are never compared. All systems publish identical members.

\paragraph{The swept parameters.} Two axes are swept rather than chosen. The
first is the input size, the number of snapshots replayed. The second is the
\emph{unit}: the amount of data one execution handles --- one message in
RDF-Connect, one line in the shell pipe, one task in CWL. At one snapshot per
unit every system streams; at all snapshots per unit every system batches.
Sweeping between the extremes places the systems on one axis instead of
picking a point on it, and the crossover is the result that does not depend on
which pipeline we chose.

\paragraph{Orchestration overhead.} A synthetic pipeline whose processors do a
configurable amount of CPU work per message isolates what the orchestrator
adds per message (\S\ref{sec:eval-overhead}). Its generator also provides
ground truth for a calibration workload with known-invalid records, on which
every system was first verified.

\paragraph{Incremental feed (B2).} See \S\ref{sec:eval-capability}.

\subsection{Results}
\label{sec:eval-results}

\paragraph{Start-up and per-record cost.} One cold process costs
\res{1.03}\,s for the mapper and \res{0.28}\,s for the validator; a record
through an already warm pipe costs \res{0.71}\,ms. One process start is
therefore worth about \res{1\,500} streamed records, and every system that
starts processes per unit pays that price per unit.

\paragraph{Input size.} Table~\ref{tab:eval-size} reports the six-stage
pipeline over \res{5} to \res{30} recorded snapshots. Per snapshot, cost falls
for every system that keeps its processes (shell \res{801}$\to$\res{238}\,ms,
RDF-Connect \res{1845}$\to$\res{473}\,ms, CWL-batch
\res{1465}$\to$\res{373}\,ms) as start-up amortises, and stays flat at
\res{1.8}\,s for CWL-scatter, which pays a task per snapshot. Intermediate
storage is where the architectures separate: CWL writes every stage's output
and every stage's state to disk, growing linearly
(\res{6.4}$\to$\res{35.1}\,MB), while the streaming systems materialise
nothing between stages.

\paragraph{Granularity: the crossover.} Sweeping how many snapshots one CWL
task handles, at \res{30} snapshots, gives \res{52.7}, \res{19.4},
\res{12.7} and \res{11.4}\,s for \res{1}, \res{5}, \res{15} and all
snapshots per task. At one snapshot per task --- the granularity the streaming
systems work at throughout --- CWL is \res{3.7}$\times$ slower than
RDF-Connect. It overtakes RDF-Connect between \res{5} and \res{15} snapshots
per task, and with a single task it reaches its own batch encoding. The
comparison the framework claims is therefore visible directly: RDF-Connect
costs \res{1.27}$\times$ of CWL's best case while keeping the granularity CWL
must surrender to reach it.

\paragraph{Records per unit.} Table~\ref{tab:eval-unit} shows the systems on
the swept axis. At one record per unit, CWL pays a task per record,
\res{0.75--0.87}\,s with \texttt{cwltool} and StreamFlow and \res{1.5}\,s with
Toil, and is \res{70$\times$} slower than RDF-Connect. As units
grow, the task cost is shared by more records and CWL overtakes RDF-Connect
between \res{100 and 1\,000} records per unit; with one unit it is within
\res{1.5$\times$} of the shell pipe. RDF-Connect's cost is dominated by a fixed
start-up of \res{4--5}\,s (orchestrator, one JVM and one Node.js runner) and a
per-message cost of \res{6}\,ms at one record per unit, against \res{1.3}\,ms
for the shell pipe. % TODO: the crossover at larger n, from anchor-unit.

\paragraph{Time to first output.} For the streaming systems the first result
arrives after start-up regardless of the input size (\res{0.8--1.1}\,s for the
shell pipe, \res{4--6}\,s for RDF-Connect). A CWL workflow produces its
results when the workflow completes, so its time to first output equals its
makespan and grows with the input.

\paragraph{Memory and intermediate storage.} RDF-Connect holds three runtimes
and peaks at \res{1.1--1.2}\,GB, independent of the unit; the shell pipe at
\res{0.4}\,GB. CWL-scatter runs up to \res{8} tasks in parallel and peaks at
\res{1.4}\,GB. Intermediate storage is where the architectures separate:
streaming systems materialise nothing between stages, while CWL stages every
chunk, its mapped output, and its report as files. % TODO: storage vs n.

\subsection{Orchestration overhead}
\label{sec:eval-overhead}

% From experiment 1 (docs/benchmark-1-results.md).
Routing every message through the orchestrator (Section~3.7) has a price that
the synthetic pipeline isolates. With processors that do no work, a message
through RDF-Connect costs \res{0.23}\,ms against \res{0.002}\,ms in-process. As
processors do more work per message, the overhead's share falls: it is
\res{35}\,\% at 1\,ms of work per message and \res{7.5}\,\% at 10\,ms. The
minimum effective task granularity, the work per message at which half the
time is still overhead, is \res{0.42}\,ms. For the RML mapping and SHACL
validation of B1, which cost \res{0.6} and \res{0.4}\,ms per record warm, the
orchestrator is therefore a visible but not dominant share of the per-record
cost; for cheaper processors it dominates.

\subsection{Capability and portability}
\label{sec:eval-capability}

\paragraph{Stateful stages under scatter.} Three of the six stages keep state:
change detection holds the previous state of every member, the fragmenter holds
its buckets, and the publisher appends to a published tree. A streaming system
keeps that state in the processor for the life of the pipeline. CWL's scatter
runs its tasks independently and offers no way to thread a value from one task
to the next, so the stateful stages cannot be scattered at all: in our encoding
they run as single tasks over the gathered stream, and their state is carried
between stages as staged directories and files. The parallelism a batch system
offers therefore stops exactly where an incremental knowledge-engineering
pipeline needs it, and the cost of making the state explicit is visible as
intermediate storage. This is a structural property, not a measurement.

\paragraph{Unbounded input.} An RDF-Connect pipeline can consume a source that
never ends and emit results as they arrive. A CWL step starts when its input
files are complete, so an unbounded stream is not slow in CWL but
inexpressible; emulating it with re-triggered micro-batches (the outline's B2)
measures the emulation. We report this as a capability boundary rather than
as a number. % Decide: keep B2 as a measured micro-batch emulation, or not.

\paragraph{Portability of a valid description.} The same valid CWL workflow
did not run unchanged on all three runners. StreamFlow wrote a tool's standard
error into the file captured as its standard output, and staged a gathered
array of files into one directory, where files sharing a name overwrote each
other; both produced wrong output silently. Toil re-runs a failed job with
more resources by default, which hides failures in the timing unless disabled.
The workarounds are small and harmless for the other runners, but they show
that a portable description does not by itself make the execution portable.
A third limit is not a defect of the description at all: StreamFlow hands a
step's command line to \texttt{sh} as a single argument, so a gather over
\res{1\,000} chunk files exceeds the operating system's 128\,KB limit on one
argument and fails after all tasks have run. Fine-grained scatter is thus
bounded not only by its cost but, on one runner, by its feasibility.

\subsection{Threats to validity}
\label{sec:eval-threats}

\begin{itemize}
\item \emph{Implementation versus paradigm.} Three CWL runners, two of which
  agree within \res{10}\,\%, guard against attributing one runner's cost to
  CWL.
\item \emph{Author bias.} We develop RDF-Connect. The parameter grid is fixed
  before the final runs, all raw measurements and the benchmark are published,
  and the regions where RDF-Connect loses (the shell pipe everywhere; CWL at
  large units) are reported as such.
\item \emph{Workload choice.} The records-per-unit sweep and the synthetic
  work sweep report surfaces rather than points, so a reader can locate their
  own workload instead of relying on ours.
\item \emph{Filesystem effects.} All systems run on tmpfs; results on disk
  would penalise the file-passing systems further.
\item \emph{Invalid data.} A unit is rejected whole when one record fails, so
  large units with broken records forward little data. Timing runs use
  \res{valid} data; correctness runs use \res{5}\,\% broken records.
\end{itemize}

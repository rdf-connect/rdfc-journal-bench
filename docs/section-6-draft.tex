\section{Comparative evaluation}
\label{sec:eval}

Table~1 says what each framework can express. It says nothing about what the
expressiveness costs, and that is the question a practitioner has when choosing
between RDF-Connect and a workflow system they already run.

Two costs are worth separating. The first is the price of the architecture
itself: every message travels from a processor to its runner, through the
orchestrator, and out to another runner, where a program calling the same
functions in one process would have passed a pointer. The second is the price
of the architecture in use, against a system built on other principles, over a
pipeline someone actually deploys.

We measure them separately, because a single experiment would confound them.
A comparison against another framework alone cannot say how much of any
difference is orchestration and how much is the workload; a microbenchmark alone says
nothing about whether the overhead matters once real processors run. Section
\ref{sec:eval-micro} therefore compares RDF-Connect against itself, with the
framework removed and nothing else changed. Section~\ref{sec:eval-pipeline}
compares it against workflow managers and against a shell pipeline on a
deployed knowledge graph publication pipeline.

Three rules apply to both experiments. Every system runs the same
implementations: the published processors, or command-line tools that
instantiate those same processor classes. No system shares warm state between
invocations, since that is part of what distinguishes them. And every run is
checked against expected output computed from the input, so a system that runs
fast by doing less work is reported as failed rather than fast.

% ----------------------------------------------------------------------------
\subsection{The cost of the architecture}
\label{sec:eval-micro}

The first experiment holds the processors fixed and removes the framework. Both
arms instantiate the same processor classes over the same workload. One is an
ordinary RDF-Connect deployment. The other is a driver that constructs the
processors in a single process and connects them with in-memory channels that
reproduce the runner's acknowledgement semantics, including the rule that a
write resolves only once the reader has consumed the message. The difference
between the arms is the orchestrator, the runners and the gRPC transport.

The workload is synthetic: a generator, a chain of pass-through processors and
a sink, parameterised by message count, message size, pipeline depth, and the
microseconds of CPU work each processor spends per message. The work parameter
is the interesting one. With no work per message, everything measured is
overhead; as the work grows, overhead becomes a shrinking share of a real cost.

With processors that do nothing, a message costs \res{0.23}\,ms through
RDF-Connect and \res{0.002}\,ms in process. The ratio is large but not the
useful number, because no processor does nothing. Adding work per message gives
the shape in Table~\ref{tab:eval-micro}: the framework adds a roughly constant
\res{0.23--0.8}\,ms per message, which is \res{35}\,\% of the total at 1\,ms of
work per message and \res{7.5}\,\% at 10\,ms.

Following Task Bench~\cite{slaughter2020}, we summarise this as a minimum
effective task granularity: the work per message at which half the time is
still framework. For RDF-Connect it is \res{0.42}\,ms. Below that granularity
the orchestrator dominates and a pipeline should batch its messages; above it
the processors dominate. The stages of Section~\ref{sec:eval-pipeline} cost
\res{0.6} and \res{0.4}\,ms per record once warm, which puts a realistic
knowledge engineering pipeline just above the threshold.

Startup is a separate fixed cost. An RDF-Connect deployment with a JVM runner
and a Node.js runner takes \res{4--5}\,s before the first message moves,
against \res{1.7}\,s for a JavaScript-only deployment. For pipelines that run
for hours this disappears; for a pipeline invoked per file in a CI job it does
not.

\subsection{A deployed pipeline against workflow managers}
\label{sec:eval-pipeline}

The second experiment takes one of the pipelines of Section~5 and runs it under
RDF-Connect, a shell pipeline, three CWL engines and Nextflow.

\subsubsection{The pipeline}

\texttt{CA-Blue-Bike-LDES} publishes the availability of a Belgian
bike-sharing service as a Linked Data Event Stream. It polls an HTTP API for
the state of every station, lifts each snapshot to RDF, detects which stations
changed, annotates the changes as stream members, fragments them by time and
writes the fragments as a static LDES. Table~\ref{tab:eval-stages} lists the
stages and the components that implement them.

\midrule

3 & change detection & \texttt{DumpsToFeed} & Node.js \\
4 & stream annotation & \texttt{Sdsify} & Node.js \\
5 & fragmentation & \texttt{Bucketize} & Node.js \\

\bottomrule

The RML mapping is the deployment's own document: nine triples maps over
mobility vocabularies, with FnO functions. One line changed, so that the
mapping reads the pipeline's channel instead of the live API. The shapes that
gate the data also describe the feed's members, which is how the deployed
DCAT-AP feeds are configured.

The input is recorded from the API the deployment consumes, so that every run
replays the same data: \res{330} stations per snapshot, \res{70} of which carry
the timestamp the mapping keys its reports on, and \res{3.6} stations changing
per minute.

\subsubsection{The systems}

\begin{description}
\item[RDF-Connect.] One pipeline description; the mapper on the JVM runner and
  the other five processors on the Node.js runner.
\item[Shell pipeline.] The six stages as command-line tools in one pipe, with
  the channels that carry stream metadata as named pipes. It runs the same
  processes as the RDF-Connect deployment with the operating system in place of
  the orchestrator, and so bounds what mediated channels and a declarative
  description can cost.
\item[CWL-batch.] One \texttt{CommandLineTool} per stage, one task each, which
  is how a CWL user writes this pipeline.
\item[CWL-scatter.] The same tools, with the input split into chunks and the
  stateless stages run once per chunk. CWL does not split files, so the split
  and the concatenation are steps of the workflow and are measured with it.
\item[Nextflow.] The same tools again, composed with channels. A process still
  runs once per item, but consumers start as items arrive, so the mapping of
  one snapshot overlaps the validation of the previous one. Among the workflow
  managers this is the closest to a streaming execution model.
\end{description}

Both CWL encodings run on three engines --- \texttt{cwltool}
\res{3.2.20260720092025}, Toil \res{9.5.0} and StreamFlow \res{0.2.0rc3} ---
from the same workflow documents, so that a difference between them is a
property of the engine rather than of the description. None uses containers.

The command-line tools are not reimplementations. A small adapter instantiates
a published processor from an RDF description of the step, materialises its
arguments through the processor's own SHACL shapes exactly as the runner does,
and connects its channels to standard input and output. Every arm therefore
runs the same processor code with the same configuration; what differs is what
carries messages between stages.

Each run is checked against output derived from the input rather than from
another system. A member is created the first time a station is observed with a
given timestamp, and updated when the data the member shape reaches changes;
both are computable from the recorded snapshots. What the shape reaches matters:
the station's total capacity, two properties away from the member, changes
without producing an update, and a check written against the station records
rather than the shape reports failures that are not there. Timestamps the
pipeline mints itself are excluded, since they differ between runs by design.
All systems published the same members and the same activities in every
configuration reported here.

\subsubsection{Setup}

One machine: \res{Intel Core i7-1185G7, 8 threads, 15\,GB RAM, Linux 7.1.3},
Node.js \res{26.4.0}, OpenJDK \res{22.0.1}, Nextflow \res{26.04.6}. Working
directories are on tmpfs, so the file-passing systems are not measured against
the disk. Each configuration runs \res{5} times and we report medians.

Each run executes inside a transient cgroup, from which CPU time and peak
memory are read. Sampling would not do here: a scattered workflow starts
thousands of processes that live for well under a second, and a process that
begins and ends between two samples contributes nothing to the total.
Intermediate storage is the largest total size of a system's working
directories during the run, sampled every 250\,ms.

\subsubsection{Results}

Table~\ref{tab:eval-size} gives the makespan by input size. Every system that
keeps its processes alive amortises startup: per snapshot, the shell pipeline
falls from \res{473} to \res{212}\,ms, RDF-Connect from \res{1568} to
\res{379}\,ms, CWL-batch from \res{1186} to \res{327}\,ms. CWL-scatter stays
between \res{1.6} and \res{1.9}\,s per snapshot, because it starts a fresh
process per stage per snapshot.

Makespan and CPU time diverge. The shell pipeline finishes first while using
\res{4.8} cores, its six stages running at once; RDF-Connect uses \res{2.6}.
Their CPU times agree to within \res{2}\,\% (\res{30.1} against
\res{29.4}\,s at \res{30} snapshots), which places the difference in
concurrency rather than in transport: a message crosses the orchestrator in
under a millisecond (\S\ref{sec:eval-micro}), but a channel admits one message
at a time, so stages advance in lock-step. CWL-batch spends the least CPU
(\res{21.8}\,s) by running one stage at a time over whole files.

Storage grows with the input for the CWL arms and stays at zero for the
streaming ones (\res{4.0} to \res{20.7}\,MB over this range). A file-passing system writes every stage's output, and here
also every stage's state, to disk; a streaming system passes them in memory.
The growth is a property of the execution model rather than of cwltool, which
is why we report it alongside makespan.

How much data one execution handles is the parameter that matters most, and it
is the one a CWL user controls by choosing a chunk size. At \res{30} snapshots,
CWL-scatter takes \res{46.5}\,s with one snapshot per task, \res{16.6}\,s with
five, \res{11.0}\,s with fifteen and \res{10.5}\,s with a single task, where it
meets its own batch encoding. RDF-Connect takes \res{11.3}\,s and the shell
pipeline \res{6.1}\,s, both processing one snapshot at a time throughout.

CPU time separates the cost of the work from the cost of the granularity. CWL
spends \res{310.9}\,s with one snapshot per task against \res{21.0}\,s with a
single task, a factor of \res{15} for identical output, since each task starts
its own JVM and Node.js runtime. RDF-Connect works at one snapshot per message
throughout for \res{29.4}\,s: \res{1.4}$\times$ the cheapest CWL run, and a
tenth of what CWL spends to reach the same granularity. Nextflow, whose
channels let stages overlap, \res{tracks CWL-scatter within 10\,\%}: the
overlap does not offset the cost of a process per item at this task size.

The descriptions can be compared as well as the runs. Describing this pipeline
takes \res{110} lines of RDF in a single document for RDF-Connect and
\res{286} lines across seven files for CWL, where every stage needs a tool
description besides its configuration and every stateful stage needs its state
wired between tasks. Inserting a further processor, skolemisation, changes
\res{10} lines of the one document against \res{31} lines across three files.
Both modified pipelines were executed rather than only counted.

\subsection{What the systems cannot do}
\label{sec:eval-capability}

Some differences are not measurable because one system cannot express the
workload at all. We report these as boundaries.

\paragraph{State across tasks.} Three of the six stages keep state: change
detection remembers the previous version of every member, the fragmenter
remembers its buckets, and the publisher appends to a tree it has already
written. A streaming processor holds that state for the life of the pipeline.
A scattered task, by contrast, is an isolated execution over staged inputs, and
neither CWL nor Nextflow can pass a value from one such task to the next. These
three stages therefore run as single tasks over the gathered stream in both
systems, and their state travels between stages as staged directories and
files. Only the two stateless stages at the front of the pipeline can be
distributed, and the state a streaming processor holds in memory appears in the
other systems as intermediate storage. This follows from the execution model,
so it holds for workflow managers of this kind generally.

\paragraph{Order.} Change detection compares each snapshot against the one
before it, which presumes the stream arrives in order. A shell pipe and an
RDF-Connect channel preserve order; a Nextflow channel does not, and gathering
its results as they complete produced \res{17} updates where \res{12} had
occurred. The workflow is correct once the gather is sorted explicitly, but the
failure is silent: the output remains well-formed RDF and the member count is
unchanged.

\paragraph{Unbounded input.} A CWL step begins when its input files are
complete. A source that never ends has no complete input file, so the pipeline
of Section~\ref{sec:eval-pipeline} cannot run in CWL in the mode its deployment
actually uses, where it polls an API every fifteen seconds and publishes
continuously. What can be run instead is a scheduled re-execution over
accumulated dumps, which is a different program with different freshness
characteristics.

\paragraph{Portability of a valid description.} The same valid CWL workflow did
not behave identically on three runners. StreamFlow wrote a tool's standard
error into the file capturing its standard output, and staged a gathered array
of files into one directory, where files with the same name overwrote each
other; both silently produced wrong output. It also passes a step's command
line to \texttt{sh} as a single argument, so a gather over \res{1\,000} files
exceeds the operating system's limit and fails after every task has run. Toil
retries a failed job with more memory by default, which hides failures in
timings. The workarounds were small, and harmless on the other runners, but a
portable description did not give us portable execution.

\subsection{Threats to validity}
\label{sec:eval-threats}

\emph{One implementation is not a paradigm.} The identical workflow ran on
three CWL engines, of which \res{two agree within 10\,\%}, and the same
pipeline ran on Nextflow, whose execution model differs. The costs we report
are therefore properties of executing a pipeline as scheduled tasks over files,
not of any one engine.

\emph{We wrote RDF-Connect.} The parameter grid was fixed before the final
runs; the benchmark, the recorded input and all raw measurements are published;
and the cases where RDF-Connect loses are reported: the shell pipeline is
faster everywhere, and CWL is faster once its tasks are large.

\emph{Parallelism differs.} The systems take different shares of the machine:
\res{4.8} cores for the shell pipeline, \res{6.9} for CWL-scatter, \res{2.6}
for RDF-Connect. Makespan alone would flatter whichever takes more, so we
report CPU time from the kernel's cgroup accounting alongside it, covering
every descendant process including the short-lived ones a scattered workflow
starts.

\emph{One machine, one dataset.} The pipeline is one deployment among the
several of Section~5, and the recorded input covers \res{24}\,h of one API.
Its stations change slowly, so the feed is dominated by first observations
rather than updates; a faster-moving source would put more load on the stages
after change detection.
The microbenchmark of Section~\ref{sec:eval-micro} is what generalises the
per-message cost beyond it.
